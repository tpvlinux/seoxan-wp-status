# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Seoxan WP Status is a single-purpose WordPress plugin: a diagnostic admin page for WordPress/WooCommerce installs. It reports on autoload option size, transients count, WooCommerce session count, and Redis object-cache hit rate, computes a 0-100 "Seoxan Score", and generates (but never executes) a block of cleanup SQL for the admin to review manually.

There is no build system, package manager, or test suite — it's plain PHP files plus one CSS file, loaded directly by WordPress's plugin loader. There is nothing to build, lint (beyond `php -l`), or test; changes are made directly to the PHP files and verified by activating the plugin in a WordPress install. The one exception is [vendor/plugin-update-checker/](vendor/plugin-update-checker/) (see **Self-updates** below): a third-party library vendored as plain files (no Composer), the only dependency in the codebase.

This repo lives at **github.com/tpvlinux/seoxan-wp-status** (public — no secrets belong in it; every real credential, API key, or token used by this plugin lives per-site, in that site's own database/`wp-config.php`, never here). To ship a new version: bump `Version:` in [seoxan-wp-status.php](seoxan-wp-status.php), commit, and create a GitHub release/tag with that same version number (`gh release create vX.Y.Z` or via the GitHub UI) — no build or asset upload needed, sites pick it up automatically (see [self-update.php](self-update.php) below).

## Architecture

The plugin is wired together in [seoxan-wp-status.php](seoxan-wp-status.php), the main plugin file WordPress loads. It defines `SEOXAN_STATUS_PATH`/`SEOXAN_STATUS_URL`, requires the other PHP files, and registers an `admin_menu` hook that adds two submenu pages under the "Seoxan Status" top-level menu — **📊 Estado** (`seoxan-wp-status`) and **🔑 API Remota** (`seoxan-wp-status-api`) — and enqueues `assets/style.css`.

- **[functions-status.php](functions-status.php)** — data-gathering layer. Each `seoxan_get_*()` function runs a direct `$wpdb` query (or, for Redis, a raw `Redis` client connection to `127.0.0.1:6379`) and returns a scalar or array. No caching, no sanitization of query results — these are read-only diagnostic reads against `$wpdb->options`, WooCommerce session tables, and `SHOW TABLE STATUS`.
- **[admin-page.php](admin-page.php)** — presentation layer for the **📊 Estado** page. `seoxan_wp_status_page()` is the callback registered for that submenu; it calls the functions above, applies threshold logic inline (e.g. autoload `< 500000` = ok, `< 2000000` = warn, else bad) to derive per-metric statuses and an aggregate score/emoji verdict, then renders the page HTML directly (mixed PHP/HTML, no template engine). A small inline `<script>` toggles a hidden "technical details" panel. `seoxan_status_color()` is the shared badge-rendering helper (used by both admin pages). The page ends with a short teaser linking to the API subpage — no API key logic lives here.
- **[sql-cleaner.php](sql-cleaner.php)** — `seoxan_generate_cleanup_sql()` builds a suggested SQL script (expired-transient deletes, stale WooCommerce session deletes, autoload-to-`no` updates for oversized options, a manual-review query for orphaned `plugin_*` options) as a string. It is only ever displayed in a `<textarea>` for the admin to copy — never executed by the plugin itself.
- **[api-key.php](api-key.php)** — API key lifecycle for the remote endpoint. `seoxan_generate_api_key()` creates a random key, returns it once in plaintext, and persists only its SHA-256 hash (`seoxan_status_api_key_hash` option, non-autoloaded) plus metadata (`seoxan_status_api_key_meta`: created/last-used timestamps and a masked preview). `seoxan_verify_api_key()` compares via `hash_equals()`. Also implements a per-IP brute-force lockout (5 failed attempts → 15 min block, via transients).
- **[api-page.php](api-page.php)** — presentation layer for the **🔑 API Remota** submenu page. `seoxan_api_settings_page()` handles the nonce-protected generate/revoke POST actions, shows key status/metadata, and documents the endpoint for the admin (URL, auth headers, `?refresh=1`, example curl request/response, security notes). This is the only place API key UI lives — kept separate from the diagnostics page by design.
- **[rest-api.php](rest-api.php)** — registers `GET /wp-json/seoxan-status/v1/updates`, `/health` (also reports this plugin's own installed version, read straight from its file header via `get_file_data()` rather than a separately-maintained constant, so it can't drift — handy for confirming what actually landed on disk without hunting through the full `/updates` plugin list, e.g. after manually reactivating it; `?check_github=1` adds a live `wp_remote_get()` connectivity check against the GitHub API, `seoxan_check_github_connectivity()`, for diagnosing a site whose self-updater never detects new releases — typically `WP_HTTP_BLOCK_EXTERNAL` without `api.github.com` allow-listed, or a hosting firewall — without needing file/hosting access) and `/last-update`, plus three write endpoints: `POST /update-plugin`, `POST /update-theme`, `POST /update-core`. `GET /last-update` returns `seoxan_get_last_update_result()` (or `{found: false}`) so a caller can check the outcome of a previously-fired update even if it didn't get the `POST` response (e.g. the connection dropped during a slow core update). `seoxan_api_permission_check()` gates every request on the API key (header `X-Seoxan-Api-Key` or `Authorization: Bearer`) plus the lockout check. `seoxan_api_updates_endpoint()` reports pending WP core/plugin/theme updates by reading `get_core_updates()` / `get_plugin_updates()` / `get_site_transient('update_themes')`; a `?refresh=1` param triggers a live `wp_version_check()`/`wp_update_plugins()`/`wp_update_themes()`, globally rate-limited to once per 5 minutes. The three `POST` endpoints delegate the actual upgrade work to [updates-runner.php](updates-runner.php) via `seoxan_api_run_update_endpoint()`, which adds a transient-based lock (no two updates run concurrently) and formats the `{success, ...}` / `{success: false, error}` JSON response (409 if locked).
- **[updates-runner.php](updates-runner.php)** — remote-update execution layer, used only from the `POST` endpoints above. `seoxan_run_plugin_update()` / `seoxan_run_theme_update()` / `seoxan_run_core_update()` drive WordPress's own `Plugin_Upgrader` / `Theme_Upgrader` / `Core_Upgrader` (with the silent `Automatic_Upgrader_Skin`, the same one background auto-updates use) to upgrade software already installed on the site — they never install a new plugin/theme, and core always upgrades to whatever WordPress has already detected as pending (no arbitrary version). All three delegate to `seoxan_run_update_shielded()`, whose single source of truth for success/failure is always the installed version before vs. after (`$get_current_version`), never just whether `$attempt()` threw — a `WP_Upgrader::upgrade()` call that returns without a `WP_Error` doesn't guarantee the files actually changed, and `Automatic_Upgrader_Skin` (unlike `WP_Ajax_Upgrader_Skin`) has no `get_errors()` to double-check with, so the three `seoxan_run_*_update()` closures only treat `$result === false` as failure and otherwise trust the version comparison. It does two things:
  - **Fatal-error shielding**: WordPress replaces the plugin/theme/core files *before* `upgrade()` returns (it fires `upgrader_process_complete` etc. afterward) — if a third-party hook (a caching plugin's cleanup, typically) calls `wp_die()` or throws there, the file swap already happened but the request dies before this plugin can log or respond, and WordPress's own JSON fatal-error envelope (not this API's `{success, ...}` shape) gets sent instead. The shield converts `wp_die()` into a catchable exception (filtering `wp_die_handler` and its `_json`/`_ajax`/`_xmlrpc`/`_xml` variants for the duration of the call), buffers all output, and — via `try/catch` plus a `register_shutdown_function` safety net for truly uncatchable fatals (OOM, timeout) — always re-verifies the actual installed version and calls `seoxan_log_update_result()` before anything tries to build the HTTP response, releasing the update lock (`seoxan_api_update_locked()`) in the process.
  - **Backup and automatic rollback**: WordPress's own WP 6.3+ temp-backup (`wp-content/upgrade-temp-backup/`) is deleted as soon as `install_package()` reports success, so it can't protect against "installed fine but the new code is broken." To cover that, `seoxan_run_update_shielded()` makes its *own* backup (`seoxan_backup_extension()`, into `wp-content/seoxan-status-backups/`) before touching anything, probes the site's front page before and after (`seoxan_probe_site_health()`) to detect a fatal, and — if the update broke the site — restores the backup automatically via `seoxan_restore_extension()`, reporting `reverted: true` plus `attempted_version`/`restored_version`. If the site was already broken *before* the update, backup/verification is skipped (nothing to meaningfully compare against). If a restore itself fails, the backup is deliberately kept (`manual_backup_path` in the result) instead of deleted, for manual recovery. Backups are always temporary: deleted in the same request once no longer needed, with `seoxan_cleanup_stale_backups()` (run both at the start of every update and via a daily `seoxan_status_cleanup_backups_event` cron, scheduled by `seoxan_schedule_backup_cleanup()` in the main plugin file) sweeping any orphaned backup older than 24h (30 days for ones kept for manual recovery) as a safety net against the process dying in a way nothing else can catch.

  - **Plugin reactivation**: `Plugin_Upgrader::upgrade()` always deactivates the plugin before swapping its files (`deactivate_plugin_before_upgrade()`), unless the request is WP-Cron (`wp_doing_cron()`) — a REST request never is. The `active_before`/`active_after` filters WordPress hooks for that case only toggle maintenance mode, and only when it *is* cron, so they reactivate nothing here; outside wp-admin's own AJAX handler (which reactivates separately), nothing else does it either. `seoxan_run_plugin_update()` does it in two layers: inside the attempt, right after upgrading (verifying with `is_plugin_active()` rather than trusting `activate_plugin()`'s return — it can fail silently, e.g. on unexpected output, more likely exactly when the plugin updates *itself* mid-request — and falling back to writing `active_plugins` directly if needed, since a plugin that was active and healthy before doesn't need `activate_plugin()`'s activation sandbox re-run), and again unconditionally right after `seoxan_run_update_shielded()` returns (covering the case where the attempt failed or fataled before ever reaching that first check, which would otherwise leave a plugin deactivated that nobody asked to turn off — critical for this plugin's own self-updates, where staying deactivated would take out the very API needed to fix it).

  Every attempt is recorded into two places: `seoxan_status_last_update` (the single most-recent action, surfaced via `GET /last-update`, which also reports the live lock state so a client can tell "still running" apart from "no record yet") and `seoxan_status_update_history` (keyed `"{type}:{target}"`, one entry per plugin/theme/`core`, surfaced as `last_remote_update` on each item in `GET /updates` — this is how a caller learns *which* plugin/theme broke the site the last time it was remotely updated). Requires the server's filesystem method to be `direct` (same requirement as updating from wp-admin, now also needed for the pre-update backup).
- **[self-update.php](self-update.php)** — makes *this* plugin update-aware, since it's not on WordPress.org (without this, `get_plugin_updates()` would never report a newer version, and `GET /updates`/`POST /update-plugin` would have nothing to act on for it). Wraps [Plugin Update Checker](https://github.com/YahnisElsts/plugin-update-checker) (MIT, vendored at `vendor/plugin-update-checker/`, no Composer) pointed at the GitHub repo above; `seoxan_init_self_updater()` is called directly (not inside a hook — PUC expects to register its own hooks as early as possible) and is otherwise invisible to the rest of the plugin: once PUC reports a new version, it flows through the exact same `site_transient_update_plugins` data that `updates-runner.php`/`rest-api.php` already read, so this plugin can update itself remotely through `POST /update-plugin` with the same backup/shielding/rollback protection as any other plugin. The repo is public, so this needs no authentication and no per-site configuration at all — it was originally built with a private repo + a distributable GitHub-token mechanism (`self-update-token` REST endpoints, a wp-config constant, a manual form), but that entire layer was removed once the repo went public, since it turned out the repo's privacy was never the plugin's real security boundary (this plugin's plain PHP source already ships, unobfuscated, to every site it's installed on) while it *did* add real operational cost (the same token still has to reach all ~500 independently-running sites somehow). If this plugin is ever made private again, that mechanism would need to be reintroduced.
- **[assets/style.css](assets/style.css)** — styling for the status badges (`.seoxan-ok`/`.seoxan-warn`/`.seoxan-bad`), the score box, the API key management box, the key-reveal callout, and the teaser box on the Estado page.

## Remote API

The **🔑 API Remota** submenu ([api-page.php](api-page.php)) is the single place to generate/regenerate/revoke the API key and see usage docs — deliberately separated from the **📊 Estado** diagnostics page so the two concerns (reading local metrics vs. exposing a remote endpoint) don't mix in one form. Regenerating invalidates the previous key immediately (single active key, no per-service keys). A generated key is shown in plaintext exactly once at creation time; only a masked preview is shown afterward. There is no capability/auth path other than the key itself — anyone with a valid key can both read update status **and trigger plugin/theme/core updates** on this site, so key secrecy is the entire security boundary; treat the key as an admin-level credential, not a read-only token. The write endpoints are intentionally limited to upgrading software already installed (see [updates-runner.php](updates-runner.php)) — they are not a general install/deploy mechanism.

## Conventions to preserve

- All functions and hooks are prefixed `seoxan_` / `seoxan-` (menu slug, CSS handle, CSS classes) — keep new code consistent with this.
- Every PHP file starts with `if (!defined('ABSPATH')) exit;` to block direct access outside WordPress.
- Data access goes through `global $wpdb`, not a custom DB abstraction.
- Thresholds and scoring weights live inline in `seoxan_wp_status_page()` — there's no config layer, so threshold changes are made directly there.
- The plugin never executes destructive SQL itself; `sql-cleaner.php` only ever produces text for manual review/execution by the admin. Preserve this separation if extending cleanup functionality.
